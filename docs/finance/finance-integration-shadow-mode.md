# Finance Integration: Shadow Mode

เอกสารนี้กำหนดขอบเขตการเชื่อมระบบต้นทางเข้าระบบการเงิน โดยไม่เปลี่ยนข้อมูลหรือ workflow เดิมในระยะแรก

## หลักการ

- ระบบต้นทางยังเป็นเจ้าของเอกสารและสถานะเดิม
- Finance Inbox เก็บ snapshot ณ เวลาที่ส่ง ไม่อ่านค่าที่เปลี่ยนภายหลังมาเขียนทับ
- ทุกรายการเริ่มที่ `pending_review` และยังไม่ใช่รายการบัญชี
- การส่งซ้ำใช้ `source_system + source_type + source_id + source_version` เป็น idempotency key
- เอกสารที่ถูกส่งกลับต้องเพิ่ม `source_version` ก่อนส่งใหม่ เพื่อรักษาประวัติเดิม
- Finance Inbox ไม่เขียนสถานะกลับระบบต้นทางใน Shadow Mode

## Source-to-Finance Mapping

| เหตุการณ์ | ระบบต้นทาง | source_type | เงื่อนไขก่อนรับ | ผลใน Shadow Mode |
|---|---|---|---|---|
| ตรวจรับงานจ้าง | purchase | service_acceptance | ตรวจรับครบถ้วน | กล่องรับรอตรวจสอบ |
| รับวัสดุเข้าคลัง | purchase/inventory | inventory_receipt | ตรวจรับและรับเข้าคลังแล้ว | กล่องรับรอตรวจสอบ |
| ขึ้นทะเบียนครุภัณฑ์ | purchase/asset | asset_receipt | มีทะเบียนสินทรัพย์ตามจำนวน | กล่องรับรอตรวจสอบ |
| ปิดคลังรายเดือน | inventoryV2 | inventory_month_close | มี snapshot ปิดเดือน | กล่องรับรอตรวจสอบ |
| นำเข้าระบบเดิม | legacy_accounting | payable_import | ผ่านการตรวจรูปแบบและจับคู่ผู้ขาย | กล่องรับรอตรวจสอบ |

## State Transition

| สถานะ | ความหมาย | เปลี่ยนไปยัง |
|---|---|---|
| `pending_review` | รับจากต้นทางแล้ว รอบัญชีตรวจ | `needs_information`, `accepted`, `rejected` |
| `needs_information` | เอกสารไม่ครบ ส่งกลับขอข้อมูล | จบ version ปัจจุบันและรอ version ใหม่ |
| `accepted` | บัญชีรับรองข้อมูลต้นทาง | พร้อมสร้างทะเบียนเจ้าหนี้ในระยะถัดไป |
| `rejected` | ไม่รับรายการพร้อมเหตุผล | สิ้นสุด |

การเปลี่ยนสถานะเปิดใช้เฉพาะการตรวจสอบเอกสารแล้ว ทุกการตัดสินใจบันทึกใน `finance_inbox_review`
และยังไม่สร้างทะเบียนเจ้าหนี้หรือรายการบัญชี

กติกาการตรวจสอบ:

- รับรองได้เมื่อข้อมูลขั้นต่ำครบ
- ขอข้อมูลเพิ่มเติมและไม่รับรายการต้องระบุเหตุผล
- รายการหนึ่งตัดสินใจได้ครั้งเดียว เพื่อป้องกัน concurrent decision
- เอกสารที่ต้องแก้ไขให้ระบบต้นทางส่งเป็น `source_version` ใหม่ ไม่แก้ snapshot เดิม

## ข้อมูลขั้นต่ำของ Purchase Snapshot

- รหัสและเลขที่ PO/สัญญา
- เลขที่และวันที่ตรวจรับ
- ผู้ขาย รหัสผู้ขาย และชื่อผู้ขาย ณ วันส่ง
- รายการ จำนวน ราคาต่อหน่วย และยอดรวม
- ประเภทปลายทาง: ค่าใช้จ่าย, คลัง, สินทรัพย์ หรืองานจ้าง
- เอกสารใบแจ้งหนี้/ใบส่งของที่มี ณ วันส่ง
- แหล่งเงิน หน่วยงาน และข้อมูลภาษีที่มี

## Reconciliation ก่อนเปิดใช้จริง

- จำนวนรายการส่งจากพัสดุเท่ากับจำนวนรายการใน Finance Inbox
- ยอดรวมเอกสารต้นทางเท่ากับยอด snapshot
- รายการวัสดุมีเอกสารรับเข้าคลัง
- รายการครุภัณฑ์มีทะเบียนสินทรัพย์ครบตามจำนวน
- รายการซ้ำถูกปฏิเสธด้วย idempotency key

## Purchase Adapter ระยะแรก

- จุดส่ง: `POST /finance/inbox/receive-purchase?id=<order-id>`
- ผู้ใช้เปิดจากแท็บ `ส่งบัญชี` ในรายละเอียดใบสั่งซื้อ/สั่งจ้าง
- Adapter อ่าน Order, รายการ, ผู้ขาย, ใบตรวจรับ และหลักฐานปลายทางเพื่อสร้าง snapshot
- วัสดุต้องมีสถานะรับเข้าคลังแล้ว
- ครุภัณฑ์ต้องมีทะเบียนสินทรัพย์ครบตามจำนวนที่ตรวจรับ
- งานจ้างต้องผ่านการตรวจรับ
- `purchase.vendor_id` ถูกเก็บเป็น `vendor_code_snapshot` เพราะเป็นรหัสธุรกิจและอาจเป็นเลข 13 หลัก ไม่ใช่ Primary Key ของทะเบียนผู้ขายการเงิน
- เมื่อส่งสำเร็จ Order status ไม่เปลี่ยน และการกดซ้ำจะเปิด snapshot เดิมแทนการสร้างรายการใหม่

## ร่างทะเบียนคุมเจ้าหนี้

- สร้างได้เฉพาะรายการใน Finance Inbox ที่ฝ่ายบัญชีรับรอง (`accepted`) แล้ว
- หนึ่ง Finance Inbox สร้างร่างทะเบียนเจ้าหนี้ได้หนึ่งรายการ เพื่อไม่ให้ตั้งหนี้ซ้ำจากเอกสารต้นทางเดียวกัน
- ต้องจับคู่กับทะเบียนผู้ขายกลางที่ยังใช้งานอยู่ โดยใช้รหัสผู้ขายเดิมเป็นตัวช่วยจับคู่ และเปิดให้ผู้ใช้ยืนยันผู้ขายเมื่อจับคู่อัตโนมัติไม่ได้
- เลขใบแจ้งหนี้ถูกปรับเป็นรูปแบบมาตรฐาน และต้องไม่ซ้ำภายใต้ผู้ขายรายเดียวกัน
- วันครบกำหนดระยะแรกคำนวณจากวันที่รับวางบิลบวกจำนวนวันเครดิต โดยเก็บฐานการคำนวณไว้ตรวจสอบย้อนหลัง
- ยอดสุทธิคำนวณจากยอดหนี้หักภาษี ณ ที่จ่าย ส่วน VAT เก็บแยกจาก snapshot ต้นทาง
- สถานะ `draft` ยังไม่ลงบัญชีแยกประเภท ไม่สร้างฎีกา ไม่เข้าแผนจ่าย และไม่ออกเช็ค
- การแก้ไขสถานะหรือข้อมูลของระบบจัดซื้อเดิมอยู่นอก transaction นี้ เพื่อให้เปิดใช้แบบคู่ขนานและย้อนกลับได้ง่าย

## การตรวจอนุมัติทะเบียนเจ้าหนี้

- Workflow คือ `draft` → `pending_approval` → `approved` หรือ `needs_revision`
- รายการ `needs_revision` แก้ไขข้อมูลร่างและส่งตรวจใหม่ได้ แต่รายการที่รอตรวจหรืออนุมัติแล้วแก้ไขไม่ได้
- การส่งกลับแก้ไขต้องมีเหตุผล และทุกการส่งตรวจ อนุมัติ หรือส่งกลับถูกบันทึกใน `finance_payable_review`
- ผู้จัดทำรายการไม่สามารถอนุมัติรายการของตนเอง เพื่อรักษาหลักแบ่งแยกหน้าที่ (maker-checker)
- ใช้สถานะเดิมเป็นเงื่อนไขขณะ update เพื่อป้องกันการตัดสินใจซ้ำหรือการกดพร้อมกัน
- ขณะเป็นร่างใช้เลข `AP-DRAFT-xxxxxx` และเปลี่ยนเป็น `AP-YYYY-xxxxxx` เมื่ออนุมัติเข้าทะเบียน
- สถานะ `approved` หมายถึงผ่านทะเบียนเจ้าหนี้เท่านั้น ยังไม่ลงบัญชี ไม่สร้างฎีกา ไม่เข้าแผนจ่าย และไม่ออกเช็ค
