## 0. บริบท & เหตุผล

Codex เขียนโมดูล laundry ไว้เป็น **เครื่องยนต์ piece-lifecycle ที่ละเอียดมาก** (จ่าย→เก็บ+ชั่ง→ซัก-อบ→นับชิ้น→รีด→QC→ล็อตสะอาด→PAR/ตู้ผ้า) แต่ **โครง flow/เมนู/dashboard ไม่ตรงกับที่เจ้าหน้าที่ใช้จริง** และเข้าใจโดเมนผิดหลายจุด งานนี้จึงเป็น **redesign ให้ตรง flow จริง + UI ดีกว่าระบบเดิม** โดยผสมกลไกภายในที่ดีของ Codex

## 1. หลักการบัญชีผ้า (เคาะกับผู้ใช้แล้ว — สำคัญสุด)

- **ผ้า = ทรัพย์สินหมุนเวียน ใช้ซ้ำ ไม่มีมูลค่า** ต่างจากวัสดุสิ้นเปลืองโดยสิ้นเชิง
- ❌ **ไม่เชื่อมพัสดุ (inventory-v2 / stock_balance) เลย** — Codex เข้าใจผิด ตัดทั้งหมด
- ✅ laundry มี **ระบบคลังของตัวเองแยกใหม่**: **คลังหลัก 1 คลัง** + **คลังย่อยรายหน่วยงาน**
- **2 สายวัด:**
  - สาย **กิโลกรัม** = รับผ้าเปื้อน→ชั่ง→ซัก→อบ (วัดปริมาณงาน/throughput ของโรงซัก)
  - สาย **ชิ้น** = คลังหลัก (ผ้าสะอาดส่วนกลาง) + สอบยอด (ทรัพย์สินผ้า รายประเภท เช่น ผ้าห่ม/ผ้าปูเตียง/เสื้อ/กางเกง)
- **จุดแปลง กก.→ชิ้น** = นับจริงหลังอบ (มีอนุมัติ) → เข้าคลังหลัก
- **คลังหลัก** = สต็อกชิ้น perpetual (เพิ่มตอนนับหลังอบ, ลดตอนจ่าย)
- **คลังย่อยหน่วยงาน** = **"ยอดตั้งต้น" (กรอบผ้าที่หน่วยงานต้องมี)** เช่น OPD เสื้อ 50 กางเกง 50 → **ไม่หักรายชิ้นทุกครั้ง** ผ้าหมุนเวียนโดยไม่นับ 1:1 (เก็บผ้าเปื้อนเป็น กก.)
- **ผ้าสูญหายสะสม** (ไปกับผู้ป่วยส่งต่อ/เสียชีวิต ฯลฯ) → ยอดจริงลดลงเรื่อย ๆ
- **สอบยอดสิ้นปี** = นับจริงรายหน่วยงาน เทียบยอดตั้งต้น → ส่วนขาด → **จัดซื้อเติมให้ครบ**

> ผลต่อสถาปัตยกรรม: **ไม่ต้องมี WARD perpetual ledger + สะพานผ้าคืน (returnCounted) แบบ Codex** — คลังย่อยใช้ ยอดตั้งต้น + สอบยอดปี พอ. `annual-count` + `ProcurementGapService` ของ Codex ตรงกับโมเดลนี้พอดี (เทียบ PAR vs นับจริง → ส่วนขาด → จัดซื้อ)

## 2. โครงเมนู (ยึดระบบเดิม + ปรับผสม)

| เมนู | ทำอะไร | กลไก |
|---|---|---|
| Dashboard | KPI นับยอด (รับ/ตรวจ/ส่ง/เบิกจ่าย) + กราฟ กก.รายเดือน/หน่วยงาน + ผ้าค้าง + เครื่อง | รื้อใหม่ (แทน flow-guide) |
| รับผ้า | เปิดรอบเก็บ ชั่ง กก. แยกเปื้อน/ติดเชื้อ รายหน่วยงาน | `collection` เดิม + UI ใหม่ |
| ตรวจรับผ้า | ตรวจสภาพ/แยกติดเชื้อ/ปฏิเสธ ก่อนยืนยันรอบ | เพิ่มขั้นใน collection |
| ซัก–อบ | batch WASH/DRY ตาม กก. | `processing` เดิม + UI ใหม่ |
| นับ–รีด–QC | นับหลังอบ→รีด→QC→เข้าคลังหลัก | `inventory` finish เดิม + UI ใหม่ |
| ส่งผ้า / เบิกจ่าย | จ่ายผ้าสะอาดจากคลังหลัก→หน่วยงาน (ชิ้นรายประเภท) ลดคลังหลัก + log ประวัติ | `issueFromLot` (ปรับ) |
| Stock คลังหลัก | ยอดคงเหลือ perpetual รายประเภท + ความเคลื่อนไหว | `balance(CLEAN)` |
| Stock คลังย่อย | ยอดตั้งต้น + ยอดนับล่าสุด + ส่วนขาด รายหน่วยงาน | PAR + annual-count |
| สอบยอดสิ้นปี → จัดซื้อ | นับจริง เทียบยอดตั้งต้น → ส่วนขาด → รายการจัดซื้อ | `annual-count` + `procurement` เดิม |
| ตั้งค่า | ประเภทผ้า / หน่วยงาน+ยอดตั้งต้น / เครื่อง / คลังรับ | รวมหน้า |

**ประเภทผ้า (ตั้งค่า):** flat list ชื่อประเภท (ผ้าห่ม, ผ้าปูเตียง, ผ้าถุง, ผ้าขวางเตียง, ผ้าเช็ดตัว, ผ้าเช็ดมือใหญ่/เล็ก, ผ้าห่อ Set …) = `laundry_item`; optional เผื่ออนาคต: น้ำหนักมาตรฐาน/ชิ้น, หมวด

## 3. กลไก Codex: เก็บ / ปรับ / ทิ้ง

- ✅ **เก็บ:** collection (กก.), processing (batch), นับหลังอบ, clean_lot, annual-count, ProcurementGapService, MachineReport, piece ledger (ใช้เป็นกลไกคลังหลัก)
- 🔧 **ปรับ:** จ่ายผ้าใช้ `issueFromLot` แต่โฟกัส "ลดคลังหลัก + log ประวัติ" (คลังย่อยไม่ perpetual); คลังย่อย = หน้ายอดตั้งต้น/สอบยอด
- 🗑️ **ทิ้ง/พัก:** WIP ตู้ผ้า cabinet-check→EXTERNAL (ผิด ตัดผ้าออกวงจร), แนวเชื่อม inventory-v2/stock_balance, WARD perpetual + returnCounted bridge

## 4. มาตรฐาน UI (ให้ "ดีกว่าระบบเดิม")

- DatepickerThai (พ.ศ.) แทน `<input type=date>` (มาตรฐาน ERP)
- page-nav pill `_menu_main` + Bootstrap Icons + รองรับมือถือ/แท็บเล็ต (ใช้หน้างานจริง)
- Dashboard = KPI cards + ApexCharts (กราฟ กก.รายเดือน, ผ้าค้าง DIRTY/QC, ประสิทธิภาพเครื่อง, หน่วยงานต่ำกว่ายอดตั้งต้น) — เพิ่มจากระบบเดิมที่มีแค่การ์ดนับ
- ตารางลิสต์คงพฤติกรรม ค้นหา/เรียง/แบ่งหน้า (แบบระบบเดิม)

## 5. เฟสการทำงาน (ทีละส่วน ปลอดภัย, commit เฉพาะไฟล์ laundry, ไม่ push จนผู้ใช้ตรวจ)

- **เฟส 0** — พัก WIP ตู้ผ้า (ปล่อยค้างไม่ commit) + สร้าง role `laundry`/`laundryApprover` + เอกสารนี้ ✅
- **เฟส 1** — เมนู/ธีม/Dashboard KPI
- **เฟส 2** — รับผ้า + ตรวจรับผ้า
- **เฟส 3** — ซัก-อบ + นับ-รีด-QC
- **เฟส 4** — ส่งผ้า/เบิกจ่าย + Stock คลังหลัก/ย่อย
- **เฟส 5** — สอบยอดสิ้นปี + จัดซื้อ + รายงาน

## 6. สิทธิ์ (RBAC)

- perm เดิม: `laundry.view`, `laundry.manage` (child ของ view), `laundry.approve` (standalone)
- role ใหม่ (เฟส 0): `laundry` → laundry.manage (เจ้าหน้าที่บันทึก); `laundryApprover` → laundry.approve + laundry.view (ผู้ตรวจ/อนุมัติ; แยกจากผู้บันทึกตามหลัก segregation)
- ผู้ใช้ผูก role ให้พนักงานเองผ่าน RBAC UI
- **ยังไม่มี department scope** — พิจารณาภายหลังถ้าต้องการให้หน่วยงานเห็นเฉพาะของตน (ตอนนี้งานซักฟอกเป็นทีมกลาง เห็นทุกหน่วยงานสมเหตุผล)
