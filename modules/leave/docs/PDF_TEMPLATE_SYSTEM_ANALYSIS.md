# การวิเคราะห์ระบบ: เครื่องมือเทมเพลต PDF แบบกำหนดตำแหน่ง (ใช้ร่วมหลายระบบ)

## วัตถุประสงค์ระบบ

- อัปโหลดไฟล์ PDF เป็นเทมเพลต
- เลือกชุดข้อมูลไปวางตามตำแหน่งที่กำหนดได้อย่างอิสระ
- ปรับ font และความหนา (และเพิ่มตัวเลือกได้ในอนาคต)
- รองรับการแสดงชื่อและส่วนรายเซ็นเป็นชุดข้อมูลเดียวกัน (ฟิลด์เดียวกันวางหลายจุด)
- นำไปใช้ได้กับหลายระบบ: ใบลา, ใบแจ้งซ่อม, ใบอื่นๆ

---

## สถานะปัจจุบัน (โมดูล Leave)

ในโมดูล leave มีระบบเทมเพลต PDF ทำงานแล้ว:

| ฟีเจอร์ | สถานะ |
|--------|--------|
| อัปโหลด PDF | มี (SettingController → uploads/leave_form_template/template.pdf) |
| กำหนดตำแหน่ง (ลากวาง) | มี (positions.php + canvas + บันทึก AJAX) |
| ฟิลด์เดียวกันหลายจุด (ชื่อ + รายเซ็น) | รองรับแล้ว (หลาย items ใช้ key เดียวกัน เช่น emp_fullname) |
| ปรับขนาดตัวอักษร (fontSize) | มี (6–24) |
| ปรับความหนา (bold) | มี |
| สร้าง PDF จริง | มี (FPDI + SetFont/SetXY/Write ใน actionLeavePdf) |
| เก็บ config | ใช้ Categorise (name = leave_form_template), data_json = { items: [...] } |

ข้อจำกัดตอนนี้: logic สร้าง PDF อยู่เฉพาะใน SettingController ของ leave และผูกกับเทมเพลตใบลาเท่านั้น — ถ้าจะใช้แนวคิดเดียวกันกับใบแจ้งซ่อมหรือระบบอื่น ต้องแยกเขียนซ้ำหรือย้าย logic ไปที่กลาง (component).

---

## แนะนำ: แบ่งเป็น Component / Module / Widget

### 1. Component (เครื่องมือหลัก — แนะนำให้อยู่ที่ `app\components`)

**บทบาท:** เป็น **เครื่องมือสร้าง PDF** จากเทมเพลต + ตำแหน่ง + ชุดข้อมูล (ไม่มี UI ไม่รู้ว่าเป็นใบลาหรือใบซ่อม)

- **ชื่อที่เหมาะสม:** เช่น `PdfTemplateFiller` หรือ `DocumentTemplatePdfGenerator`
- **หน้าที่:**
  - รับ: path ไฟล์ PDF เทมเพลต, รายการ items (key, x, y, fontSize, bold, enabled, [fontFamily ถ้าขยาย]), array values (key => ข้อความ)
  - ใช้ FPDI โหลดเทมเพลต → วน items ที่ enabled → SetFont / SetXY / Write ตามค่าที่ส่งมา
  - ส่งคืน: binary PDF (string) หรือ path ไฟล์ ตามที่เรียกใช้
- **ข้อดี:** ใช้ร่วมได้ทุกโมดูล (leave, แจ้งซ่อม, อื่นๆ) โดยไม่ซ้ำโค้ด; ทดสอบและดูแลง่าย
- **หมายเหตุ:** ตามกฎขอบเขตงาน leave — ไฟล์ใน `app\components` อยู่นอกโมดูล leave ดังนั้นการสร้าง/แก้ component นี้ต้องทำโดยทีมที่ได้รับสิทธิ์แก้ไขนอกโมดูล leave หรือแจ้งผู้ดูแลระบบ

**สรุป:** ส่วนที่ควรเป็น **Component** = ตัว “เครื่องมือเติมข้อมูลลง PDF” (engine) ให้อยู่ที่ `app\components` แล้วให้ทุกระบบเรียกใช้

---

### 2. Module (หน่วยงานที่ใช้เทมเพลต + จัดการ config)

มีได้สองแนวทาง:

#### แนวทาง A: แต่ละระบบมีหน้าตั้งค่าเทมเพลตของตัวเอง (เหมือน leave ตอนนี้)

- โมดูล **leave**: หน้าอัปโหลดเทมเพลตใบลา + กำหนดตำแหน่ง + เก็บ config (Categorise หรือโมเดลใน leave)
- โมดูล **แจ้งซ่อม** (ถ้ามี): หน้าอัปโหลดเทมเพลตใบแจ้งซ่อม + กำหนดตำแหน่ง + เก็บ config ของใบแจ้งซ่อม
- เวลาพิมพ์: แต่ละโมดูลเตรียม `templatePath`, `items` (จาก config), `values` (จากโมเดลของตัวเอง) แล้วเรียก **Component** สร้าง PDF

**ข้อดี:** แต่ละระบบควบคุมเทมเพลตและฟิลด์ของตัวเองได้เต็มที่  
**ข้อเสีย:** หน้าอัปโหลด/กำหนดตำแหน่งอาจมีโครงสร้างคล้ายกัน → ถ้าต้องการลดซ้ำอาจทำเป็น partial view หรือ widget ร่วมกัน

#### แนวทาง B: โมดูลรวมศูนย์ “เทมเพลตเอกสาร” (เช่น document-templates)

- โมดูลเดียวจัดการหลาย “ประเภทเอกสาร” (ใบลา, ใบแจ้งซ่อม, …)
- แต่ละประเภทมี: ไฟล์ PDF เทมเพลต + config ตำแหน่ง (items)
- ระบบอื่น (leave, แจ้งซ่อม) ไม่เก็บไฟล์/ config เอง แค่ “ลงทะเบียน” ประเภทเอกสาร แล้วเรียก API/component พร้อม template id + data
- การสร้าง PDF ยังใช้ **Component** เดิม

**ข้อดี:** จัดการเทมเพลตและสิทธิ์ที่เดียว  
**ข้อเสีย:** ต้องออกแบบโมดูลใหม่และอาจต้องแก้ routing / สิทธิ์ของหลายโมดูล

**สรุป:** ส่วนที่ควรเป็น **Module** = การจัดเก็บเทมเพลต + config + หน้า UI (อัปโหลด, กำหนดตำแหน่ง). จะเป็นแบบ A (แยกต่อโมดูล) หรือ B (โมดูลรวม) ขึ้นกับนโยบายของโปรเจกต์

---

### 3. Widget (ส่วน UI ย่อย — ไม่บังคับ)

**บทบาท:** ชิ้นส่วน UI ที่ใช้ร่วมได้ในหลายที่

- ตัวอย่าง:
  - **เลือกเทมเพลต:** dropdown เลือกเทมเพลตจากรายการ (ใช้ได้ในฟอร์มใบลา / ใบแจ้งซ่อม ถ้ามีหลายเทมเพลต)
  - **ปุ่มพรีวิว PDF:** กดแล้วเปิดหน้าต่าง/iframe แสดง PDF ที่สร้างจาก template + data ปัจจุบัน
- ไม่จำเป็นสำหรับ flow หลัก “อัปโหลด → กำหนดตำแหน่ง → พิมพ์” แต่ช่วยให้ UX สม่ำเสมอและลดการเขียนฟอร์มซ้ำ

**สรุป:** ส่วนที่ควรเป็น **Widget** = ส่วน UI ย่อยที่ใช้ซ้ำได้ (เลือกเทมเพลต, พรีวิว) ไม่ใช่ตัว engine สร้าง PDF

---

## สรุปตาราง: ส่วนไหนอยู่ที่ไหน

| ส่วน | แนะนำ | หมายเหตุ |
|------|--------|----------|
| **เครื่องมือเติมข้อมูลลง PDF (engine)** | **Component** (`app\components`) | รับ template path + items + values → ส่งคืน PDF; ใช้ร่วมทุกระบบ |
| **การจัดเก็บเทมเพลต + config + หน้าอัปโหลด/กำหนดตำแหน่ง** | **Module** | แยกต่อโมดูล (A) หรือโมดูลรวมศูนย์ (B) |
| **ฟิลด์เดียวกันหลายจุด (ชื่อ + รายเซ็น)** | ไม่ต้องออกแบบใหม่ | ใช้โครง “หลาย items ชุด key เดียวกัน” เหมือน leave ได้เลย |
| **ปรับ font / ความหนา / ตัวเลือกเพิ่ม** | เก็บใน config (items) + Component อ่านใช้ | ขยาย items ให้มี fontSize, bold, fontFamily (ถ้าต้องการ) |
| **เลือกเทมเพลต / พรีวิว PDF** | **Widget** (ถ้าต้องการ) | ไม่บังคับ |

---

## ขั้นตอนแนะนำถ้าจะทำให้ใช้ร่วมหลายระบบ

1. **แยก engine เป็น Component**  
   สร้าง `app\components\PdfTemplateFiller` (หรือชื่อที่ตกลง) — ย้าย logic จาก `SettingController::actionLeavePdf` ส่วนที่เกี่ยวกับ FPDI + วน items + Write ออกมาให้รับพารามิเตอร์ทั่วไป (templatePath, items, values, [options ฟอนต์]).

2. **ให้โมดูล leave ใช้ Component**  
   ใน `SettingController::actionLeavePdf` ให้เตรียม `items` กับ `values` จาก config และ Leave model แล้วเรียก Component สร้าง PDF แทนการเขียน FPDI ใน controller โดยตรง.

3. **ระบบอื่น (เช่น ใบแจ้งซ่อม)**  
   - ถ้าใช้แนวทาง A: สร้างหน้าตั้งค่าเทมเพลตในโมดูลนั้น + เก็บ config ของตัวเอง แล้วเรียก Component เดียวกันกับชุด items/values ของใบแจ้งซ่อม.  
   - ถ้าใช้แนวทาง B: ลงทะเบียนประเภทเอกสารในโมดูลเทมเพลต แล้วระบบอื่นส่ง template id + data ไปให้ Component (หรือ service ที่ wrap Component).

4. **ขยายตัวเลือก (font / ความหนา)**  
   - ใน config (items) มีอยู่แล้ว: fontSize, bold.  
   - ถ้าต้องการฟอนต์อื่น: เพิ่ม key ใน item (เช่น fontFamily) และให้ Component อ่าน key นี้แล้วใช้ SetFont ตามนั้น.

---

## หมายเหตุเกี่ยวกับกฎขอบเขตโมดูล Leave

- ตามกฎ **leave-module-only**: ไฟล์ภายใต้ `modules/leave/` แก้ไขได้เท่านั้น; ไฟล์นอกโมดูล (รวม `app\components`) ห้ามแก้โดยตรงจากขอบเขตงาน leave.
- การ **สร้าง Component ใหม่** ที่ `app\components` จึงต้องทำโดยทีม/ผู้มีสิทธิ์แก้ไขนอกโมดูล leave หรือแจ้งผู้ดูแลระบบให้สร้างจากเอกสารวิเคราะห์นี้.
- โมดูล leave ปัจจุบันใช้ `app\models\Categorise` สำหรับเก็บ config เทมเพลต (มีอยู่เดิม); การใช้โมเดลนอกโมดูลผ่าน controller ที่มีอยู่แล้วถือว่าไม่ขัดกฎที่ว่า “ไม่สร้าง/แก้ให้ไปเรียกโมเดลนอกโมดูลโดยตรงในขอบเขตงาน leave” ในลักษณะเพิ่มใหม่.

---

*เอกสารนี้ใช้สำหรับวิเคราะห์และออกแบบเครื่องมือเทมเพลต PDF ให้ใช้ร่วมหลายระบบ (ใบลา, ใบแจ้งซ่อม และอื่นๆ) และระบุว่าส่วนไหนเหมาะสมเป็น Component, Module หรือ Widget.*
