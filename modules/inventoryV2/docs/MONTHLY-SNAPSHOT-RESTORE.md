# คืนยอดยกไปจาก Excel ที่รับรองแล้ว

## ขอบเขต

คืน `closing_qty`, `closing_value` และหน่วยนับตามแถว Excel ที่จับคู่แล้ว เพื่อให้ยอดยกมาเดือนถัดไปตรงกับยอดที่ส่งบัญชี
ยึดจำนวนปลายงวดตามไฟล์ แม้จำนวนยกมา + รับ - จ่ายไม่เท่ากับจำนวนปลายงวด ผู้ใช้รับรองหลักการนี้แล้ว
ไม่ได้กู้รายงานกรกฎาคมทุกช่อง: opening, receipt, issue และ split รพ.สต./โรงพยาบาลยังคงเดิม
ไฟล์นี้ไม่มี split รายรายการ จึงไม่อนุมานการกระจายยอดหรือปรับเอกสาร/stock_balance/FIFO
หน้ารายงานแสดงข้อความชัดเจนเมื่อยอดยกไปถูกคืนจากไฟล์และอาจไม่ตรงสูตรของช่องอื่นที่ยังเป็นข้อมูลเดิม

## การใช้งาน

1. รายงาน → ตรวจไฟล์ยอดปิดเดือน: ตรวจอย่างเดียว หรือเลือก **เตรียมคืนยอดจากไฟล์**
2. ระบบเก็บไฟล์ผ่าน filemanager ด้วย ref เฉพาะชุด + SHA-256 และสร้าง draft
3. เลือกคลัง/รหัสตามแถวต้นฉบับ รหัสซ้ำห้ามรวมเข้าคลังและรหัสเดียวกันสองแถว
   คลังเดียวเป็นข้อเสนอเริ่มต้นที่ผู้ตรวจต้องรับรองในขั้นยืนยัน รายการหลายคลังไม่เดาจากยอด
4. แถวที่ไม่ตรงทะเบียนยกเว้นได้เฉพาะศูนย์ทุกช่องพร้อมเหตุผล หรือจับคู่รหัส MATER ที่ถูกต้อง
   รายการที่หน่วยต่างกันต้องยืนยันหน่วยนับ ไม่คำนวณอัตราแปลงเอง
5. หากมี snapshot งวดถัดไป ต้องยืนยันสำรองและยกเลิก snapshot เหล่านั้นก่อน (เอกสารรับ–จ่ายไม่ถูกลบ)
6. บันทึกการจับคู่และตรวจตัวอย่าง: แสดงรายการก่อน–หลังและผลต่าง ต้องครอบคลุมยอดเดิมที่ไม่เป็นศูนย์
7. **คืนยอดและล็อกงวด** บันทึกภายใน transaction เดียวทุกคลัง เก็บ before/after ครบทุกช่องของ snapshot และผู้ดำเนินการ
8. ปิดเดือนถัดไปตามปกติ จะใช้ยอดยกไปงวดรับรองเป็นยอดยกมา

สิทธิ์: `inventoryStockRepair` และเข้าถึงทุกคลังหลัก สำหรับทุก action รวมดู draft, commit, revert
การเขียนรับเฉพาะ POST ผ่าน CSRF ตาม Yii ปกติ ยอดที่เขียนอ่านจากไฟล์ที่เก็บไว้เท่านั้น ไม่รับจำนวน/มูลค่าจาก POST
ชุดเดิมที่บันทึกแล้วไม่บันทึกซ้ำ การอัปโหลดไฟล์ SHA-256 เดิมจะพากลับไป draft/ชุดที่บันทึกเดิม

## การป้องกันและย้อนคืน

- ใช้ MySQL named lock ร่วมกันระหว่างปิดเดือน, autofix, period-set, cancel-close, backfill, restore, revert
- ตรวจ SHA-256 และ fingerprint ใหม่ก่อนเขียน ปฏิเสธเมื่อข้อมูลเปลี่ยนหลัง preview
- งวดล็อกห้ามปิดซ้ำ/ยกเลิก/ตั้งยอดทับ และป้องกันที่ persistMonthlyRows กับ entry point console
- Autofix และการวิเคราะห์เริ่มหลังงวดรับรองล่าสุดของแต่ละคลัง ใช้ snapshot ที่ล็อกเป็นยอดตั้งต้น
  และคำนวณถึงงวดที่เลือกเท่านั้น การเติมราคาทุนจำกัดวันที่รับเข้าภายในช่วงนี้
  การย้ายจำนวนรับไม่ข้ามกลับเข้างวดที่ล็อก การซ่อมงวดที่ล็อกหรือก่อนหน้างวดรับรองถูกปฏิเสธ
  หากไม่มีงวดรับรองยังใช้ช่วงจากเอกสารแรกเหมือนเดิม หากยอดของงวดล็อกหายจะหยุดแทนการคำนวณย้อนหลัง
  ยอดผิดจากประวัติเก่าที่ต้องชดเชยควรใช้รายการปรับปรุงในงวดที่เปิดพร้อมหลักฐาน
- การย้อนคืนต้องยังไม่มีข้อมูลเปลี่ยนหรือปิดงวดใหม่หลัง commit และไม่มีงวดรับรองอื่นภายหลัง
- ย้อนคืน snapshot ทุกช่องพร้อม ID เดิม รวมงวดถัดไปที่เคยยกเลิก; เพิ่ม audit event ใหม่ ไม่ลบประวัติ commit
- ไม่มี endpoint แก้หรือลบ audit/ไฟล์ต้นฉบับใน workflow นี้ และ migration ไม่ลบประวัติผ่าน safeDown อัตโนมัติ

## การติดตั้ง

Migration: `m260908_090000_create_monthly_restore` สร้างเฉพาะ
`stock_monthly_restore`, `stock_monthly_restore_event`, `stock_monthly_period_lock` ไม่เปลี่ยนยอดเดิม
บนเครื่องทดสอบติดตั้งเฉพาะ migration นี้แล้ว ก่อนติดตั้งฐานจริงต้องตรวจรายการ migration pending และสำรองตามกระบวนการของระบบ
ก่อน migration หน้าตรวจอย่างเดียวยังใช้ได้ แต่ไม่เปิดปุ่มเตรียมคืนยอด

ตรวจผ่าน CLI (อ่านอย่างเดียว):

```sh
php yii monthly-snapshot/check /app/path/to/source.xlsx 2026 7
```

## การทดสอบ

`MonthlySnapshotReconciliationServiceTest`: รูปแบบไฟล์, งวด, สูตร/cached summary, ช่องว่าง, รหัสซ้ำและการเทียบคลัง

`MonthlySnapshotRestoreServiceTest`: SQLite แยกและไฟล์ชั่วคราว ไม่อ่าน config/db.php
ครอบคลุม literal quantity, ยอดยกมางวดถัดไป, idempotency, stale preview, ไฟล์ถูกแก้,
audit ล้มเหลว rollback ทุกยอด/lock, ย้อนคืน, ปฏิเสธย้อนคืนเมื่อมีงานใหม่,
การป้องกัน action เดิมก่อน side effects, duplicate mapping, skip nonzero และ server-rendered form/CSRF/XSS

MySQL บนเครื่องทดสอบตรวจ named lock ด้วย connection ที่สองแล้ว ไม่สามารถเข้าถือ lock ซ้อนกัน
ตรวจ hash snapshot ก่อนและหลังติดตั้ง/เตรียม draft แล้วตรงกัน ไม่มีการคืนยอดจริงจากขั้นเตรียม

ยังต้องทดสอบ flow หลังเข้าสู่ระบบด้วยผู้ตรวจจริงและยืนยัน mapping ของไฟล์กรกฎาคมก่อน commit
